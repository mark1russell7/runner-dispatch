# Roadmap

This file is the plan of runner-dispatch. The Status page of the site reads it, and the tracker of the project mirrors it.

| ID | Item | Status | Summary |
| --- | --- | --- | --- |
| R1 | The first package: the records and the policy | done | `@mark1russell7/runner-dispatch` has the records of a run, a job and a machine, the run label, and the trust rules as a document. The policy is a function from the record of a run to trusted or not trusted, with each reason. Property tests hold it: a run from a fork is not trusted, for each value of the other fields. |
| R2 | The check on the machine | done, 2026-11-10 | The job-started script of the runner. It tests the policy again from the event file of the job, and it compares the run with the run of the machine. The parts are `checkJob`, the settings document `machine-check/1` and the program `src/cli/job-started.ts`, with tests. Probes measured the sequence for the runner program 2.338.2: the script is the second step of a job, before each image pull and each step, and its failure skips them. A job cannot give the script a variable, and cannot change the script. The documentation does not state these facts. Two probes then started the real program on a runner, with the Node.js of the runner program. It let the job of its run start, and it refused the job of a different run before each step. Each new version of the runner program must pass these probes. |
| R3 | The state machine of a machine | done, 2026-11-10 | The life of one machine is a document of `@mark1russell7/algebra`: `MACHINE_LIFECYCLE`, with the states asked, made, registered, busy, done and destroyed. Each state that is not final has one timer. Before done, a timer that fires sends the machine to done. In done, the dispatcher asks the provider again, and each wait is two times the wait before it. Thus each path ends in destroyed, and the dispatcher forgets no machine. The functions `startLife`, `advance`, `waitOf`, `due` and `longestLife` read the document, with the times of the document `machine-times/1`. `longestLife` gives the longest time from the request for a machine to the end of its work. Tests replay each life of a simulated loop on the document. |
| R4 | The GitHub source | in progress | Part 1 is done: the source of runners of a repository, on a port of the REST API, with a fake API and a property test on the fake world. Part 2 is done: `createRestClient` of `@procedures/gh`, with conditional requests and limits of the rate. The program of the service uses it after its npm release. Part 3 is done: the runners of an organization. Each view names its scope, and the plan removes a registration of a scope one time. `checkRunnerGroup` examines that a runner group admits only the served repositories. A test with a real credential then measures the smallest permissions, the cost of an answer 304, the labels of a one-job runner and the runner groups of the Free plan. An open point: with an organization, each view lists the same runners. One list for each pass lowers the count of requests. |
| R5 | The Proxmox provider | in progress | Part 1 is the provider, on a port of the API of Proxmox VE, with a fake API and a property test. It makes a linked clone of a template in a pool. It writes the configuration into the guest through the guest agent, because the API cannot write a cloud-init file. The description of each VM keeps the record of its machine, and a destroy of a machine that is not there succeeds. The image has its own time limit for a machine with no dispatcher. Part 2 is the client of the API on a transport port, with no type of a platform, and the program of the service. The program reads one document `dispatcher-program/1` and two secrets from the environment. With an organization, it checks the runner group before its first pass. It examines the declaration with `lint`, and it starts a probe server for the liveness. Part 3 is the command line `src/bin.ts`, on the REST client of `@procedures/gh`. With `--check`, it prepares the program and starts nothing. Each line of its output goes through `redactSecrets` with the two tokens. Part 4 is a test on a real host of Proxmox VE. |
| R6 | The dispatcher service | done, 2026-11-10 | The dispatcher joins a source, the policy and a provider through two ports. `plan` is the decision of one pass, as a function with no effect. `createDispatcher` does a pass: it reads the facts, and it sends the requests of the plan. The settings document `dispatch-settings/1` gives the prefix, the capacity and the sizes. After a new start, the first pass adopts each machine of the provider. The stop switch destroys each machine. `@runner-dispatch/dispatcher` declares the loop on `@mark1russell7/service`, with a liveness check for a pass that does not end. Tests on a fake world hold it: each served job of a trusted run ends one time, and no step of a different run starts. |
| R7 | The tests of the gate | open | Tests on real jobs: a fork that names the label, a fork that takes the label of a trusted run, the sequence of the check, `pull_request_target`, the stop switch, the network of a machine, a clean machine after a job, and a stop of the dispatcher in the middle of a job. |
| R8 | The measures | open | The queue time, the start time of a machine and the job time of each job, as records. |
| R9 | The first release to npm | open | The package gets its build, its `publishConfig` and its API report, and it loses `private`. The release needs the bootstrap of a new package (`RELEASING.md`). It comes before the first deployment of the service. |
| R10 | The demonstration on the site | open | A live page of the site. A visitor changes the trust rules and a run, and sees the decision with each reason. The page also shows the life of a machine: the visitor sends events, and sees the state, the timer and the requests. It uses the functions of the package, with no server. |
